# herdr-agent-sessions

Pi tools that open a Pi session inside a Herdr worktree, so an orchestrator can delegate a COMPLETE job to another orchestrator session instead of to a subagent, plus a notification when that session really finishes and the usage rules. Spec: this file, up to `## Log`.

## Specs

S25. A tool opens a Pi session in a Herdr worktree, and only in a worktree. Verbatim: "agregaremos tools en pi para poder crear/abrir sessiones de pi con herdr o sea, crear un nuevo panel ejetutando pi. Pero esto solo como worktree, quedando como un sub space, la funcion era herdr qorktree o algo asi. y aji dentro se ejecuta pi para abrir agente" and "Asi que solo agrega la tool para crear/abrrir session con herdr worktree (crear nueva o abrir existente, asi que recibiria de parámetro el worktree y opcionalmente el id de la session si es para reanudar)" and "Tiene que ser worktree y nonpath, de modo que se limite al proyecto git y no se vaya a otros". Decisions fixed here so nothing is guessed: the tool is `worktree_session_open`, in the same `worktree_*` family as create/list/close, with `worktree: string` (required — the NAME `worktree list` prints, or a branch name), `session?: string` (a Pi session id or path, to RESUME; absent means a new session), `name?: string` (the agent/pane name, defaulting to the worktree name) and `notify?: boolean` (default true, see S26). Scope is enforced, not documented: the worktree resolves through the S24 name resolver against THIS repository's registered live worktrees only, and a path — absolute or relative — is refused with an actionable message, so no command can ever run outside a worktree of this repo. Launching is composed, because no single Herdr command starts a worktree AND a command in it: neither `herdr worktree create/open` nor `herdr pane split` accepts a command, while `herdr agent start <NAME> --kind <KIND> --pane <ID> [-- [AGENT_ARG]...]` starts an interactive agent in an EXISTING pane that is at a shell prompt. So: ensure the worktree has a Herdr workspace and pane (a worktree this plugin created already has one; for a worktree git lists but Herdr does not, `herdr worktree open --branch <b> --cwd <root> --no-focus`), then `herdr agent start <name> --kind pi --pane <pane_id> --timeout <ms> -- <pi argv>`, where the Pi argv is `--name <name>` plus `--session <id>` when resuming or `--session-id <minted>` for a new session so the id is known immediately and returned to the caller. The pane's cwd is the worktree, so Pi's own default session directory is the worktree's. Success text is `worktree session open: <worktree> <session-id>`, and `details` carries `{worktree, branch, path, paneId, workspaceId, sessionId, resumed, agentName, notify}`. The `herdrArgv` allowlist gains exactly the commands and flags this uses (`worktree open`, `agent start`, `agent get`, `agent list`) and keeps its two refusals: never `--trust-repository`, and never `--focus`. The version floor stays 0.9.4 because every flag above was run against the installed binary before this spec was written.

S26. Creating the session subscribes the creator, which is notified when that session REALLY finishes. Verbatim: "Ademas al igual que con las funciones de gentle shell de background jobs y sub agentes, agregaremñs notificaciones. Quien cree la session de pi con herdr en un worktree se suscribe a el pars recibir notificaciones de su trabajo cusndo terminar (termina real, ya lo tiene el plugin, que es cuando se detiene y no tienes jobs o subagents corriendo)". "Really finished" is this plugin's own definition, already computed for its own session and not Herdr's turn state: the delegate reads `idle` — settled, no background jobs, no subagents, no pending ask, no review in flight (`NATIVE_STATES` and `computeNativeState` in `extensions/gentle-herdr-state.ts`) — AND it was observed `working` at least once, so a delegate that never started can never be reported as finished. The state is read from what the target publishes to Herdr (`herdr agent get <target>` / `herdr agent list`: its `agent_status` plus the `gentle_state_*` metadata tokens this plugin publishes), polled on a bounded interval, with a launch grace window and a maximum wait; a target whose pane or agent disappears is reported as vanished, never as a finish. Delivery is a custom message to the CREATING session, `customType` `herdr-agent-sessions.finished`, sent as `{deliverAs: "followUp", triggerTurn: true}` — the route incoming session messages already use, because the orchestrator has to act on it (verify, merge, report). A delegate that never reported any state and a target that vanished use the same route but never claim a finish; the message says which of the three it observed. Honest limits recorded rather than hidden: the state is another process's published view, so "never started" and "never reported anything" are indistinguishable, and the message says so; and `notify: false` turns the subscription off for a caller that only wants the session opened.

S27. The usage rules live in a markdown file that is created but NOT injected yet. Verbatim: "Igual crea un .md de reglss para el manejo y uso de estas tools, seria system prompt, de momento no lo incluiremos en el plugin, solo lo creafemos (comonel de gentle shell que tiene las de orchestrator que inyecta en el system prompt, creo que inyecta al final para tema de cache). agrega esta funcion pero no inyectes aun el .md almplugin hasta que lo pida, pars poder puede que le agruge maworktrees" and "Las reglas serian worktrees.md o algo asi, que diria que pars nuevos trabajos de odd cree un nuevo worktree y se mueva a el y trabaje. Si son varios trabajos odd (diferentes grupos de issues) cree varios worktrees y cree/abra varias sessiones y delegue a cada orchestrator(session) que trabaje en cada una de los grupos de issues u odd feactures" and "Además de avisar en dicha delegacion de que en paralelo estan trabajando las otras sessiones en tal tema/odd y que si implementa un cambio relacionado o que deba saber esa session (le compete o afecta lo que trabaja/impelenta) le avise para que este al tanto de los nuebos cambios que vendra para que lo tenga en cuenta, gentle shell tiene para mandsr mensajes entee sessiones ya". Decisions fixed here: the file is `rules/worktrees.md`, written in this slice and NOT wired — no `before_agent_start` handler is added, so the system prompt is byte-identical until the user asks for the injection. The injection recipe is recorded in the documentation but not implemented: gentle-shell appends at the END of the prompt through `appendSystemPromptOnce(event.systemPromptOptions, …)` inside `pi.on("before_agent_start", …)`, which is prompt-cache friendly by construction because an unchanged prompt keeps its prefix. Content: new ODD work gets its own worktree and works there; several ODD jobs (different issue groups) get several worktrees and one orchestrator session each, opened with `worktree_session_open`; the delegation states which other sessions are working in parallel and on what topic, and asks the delegate to message the affected session when it implements something related — Gentle Shell already provides session-to-session messaging for that.

L31. Ground measured before specifying anything, so the specs rest on the installed tools and not on a guess. Herdr is 0.9.4 and its CLI is the authority: `herdr worktree create|open` and `herdr pane split` take NO command (so a pane is a shell prompt), while `herdr agent start <NAME> --kind <KIND> --pane <ID> [OPTIONS] [-- [AGENT_ARG]...]` starts a supported interactive agent in an EXISTING pane and lists `pi` among its kinds, with `--timeout <MS>` waiting for interactive readiness; `herdr agent wait <TARGET> --until <STATUS>` accepts `idle|working|blocked|done|unknown`; and `herdr agent list` reports per agent the `agent_status`, the `agent_session.value` (the Pi session file), `cwd`, `pane_id`, `workspace_id` and the `gentle_state_*` metadata tokens this plugin publishes, which is what makes a peer's finish observable at all. A reference repo (`pi-herd`) uses a different `agent start` flag shape (`--cwd/--workspace/--split`); that form does not exist in the installed binary, so it was discarded rather than copied. Pi's own session surface is `--continue`, `--resume`, `--session <path|id>`, `--session-id <id>`, `--fork`, `--session-dir`, `--name`, and its files live under `~/.pi/agent/sessions/<encoded-cwd>/<timestamp>_<id>.jsonl`; opening the same file with a DIFFERENT cwd is not documented, so a new session is minted with `--session-id` and a resume uses `--session <id>` from the worktree's own cwd. This plugin's "really finished" already exists as the `idle` branch of `computeNativeState` (settled, no background jobs, no subagents, no ask, no review) over `NATIVE_STATES = ["working","blocked","idle"]`. gentle-shell's rules are NOT a markdown file: its harness is built in code and appended at the END through `appendSystemPromptOnce` inside `pi.on("before_agent_start", …)`, which is the injection point recorded for S27. Cross-session messaging already exists in gentle-shell as `orchestrator_session_id`, `orchestrator_consult`, `orchestrator_list` and `orchestrator_send_message`, addressed by stable routing session id, and an incoming message is delivered as `pi.sendMessage({…}, {deliverAs: "followUp", triggerTurn: true})` — the route S26 reuses. Nothing in this repository provides peer messaging or a finish subscription today, so both are built here rather than assumed.
